## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted source .docx → CloneStyles | A template .docx opened via `opc.Open` (which enforces OPC-07 safety limits: zip bomb, path traversal, max parts) crosses into the cloner's byte-copy path. Source parts are read via `Part.Open` (capped at `MaxPartBytes` = 128 MiB) and written into the target via `MarkModified`. The cloner never parses the source parts (D-09) — no XML decoder runs on clone, so malformed XML does not surface here (it surfaces at resolve time per D-07). |
| CloneStyles → target package | The 5 source parts' bytes + 5 new relationships + 5 content-type Overrides cross into the target package. All part names are compile-time constants (the `cloneParts` table) — no user-supplied names reach `MarkModified`, `ContentTypes.Overrides`, or `Relationship.Target`. Path traversal is structurally impossible in the cloner. |
| cloned target → 02-01/02-02 resolver | The cloned parts' bytes cross into the resolver's lazy parse path when `ResolveParagraph`/`ResolveRun` is called over the cloned target. This boundary is owned by 02-01 (styles.xml parse) and 02-02 (theme1.xml + numbering.xml parse) — their threat models (T-02-01 through T-02-11) cover it. Plan 02-04's corpus_test.go exercises that boundary end-to-end but does not add new threats there. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-12 | Tampering / Path Traversal | `CloneStyles` — writing parts outside the target package | high | mitigate | All 5 part names are compile-time string constants in the `cloneParts` table (word/styles.xml, word/numbering.xml, word/fontTable.xml, word/theme/theme1.xml, word/settings.xml). No user-supplied or source-derived names reach `dst.MarkModified`, `dst.ContentTypes.Overrides`, or `Relationship.Target`. The cloner does not read source relationship targets to decide what to clone — it clones a fixed, hardcoded set. Path traversal is structurally impossible (no `path.Join`, no user input in part names). Additionally, `opc.Open` already ran `validatePartName` on every source entry (package.go:352-380 rejects absolute paths, `..`, backslashes, drive letters, non-UTF-8), so even a hostile source .docx cannot introduce a malformed part name that the cloner would copy — the source parts are already validated. `opc.Save` re-validates the relationship graph (relationships.go:161-191) and content-type presence (package.go:280) before writing, so a corrupted target state is caught at save time. |
| T-02-13 | DoS / Resource Exhaustion | `CloneStyles` — reading source part bytes into memory | medium | mitigate | `Part.Open` enforces `MaxPartBytes` = 128 MiB per part via `capReader` (package.go:78-83 returns `ErrDecompressionLimit` past the cap). `opc.Open` enforces `MaxTotalBytes` = 512 MiB across all parts (package.go:161-164). The cloner reads one part at a time via `io.ReadAll` on the capped reader; peak memory is bounded by the largest single part (≤128 MiB), not the sum. The 5 cloned parts together are typically < 1 MiB in practice (styles.xml ~50 KiB, theme1.xml ~10 KiB, numbering.xml ~20 KiB, fontTable.xml ~5 KiB, settings.xml ~5 KiB). No unbounded allocation. |
| T-02-14 | Tampering | `CloneStyles` — partial clone on non-empty target (atomicity violation) | high | mitigate | D-08 precondition scan: the cloner iterates all 5 `cloneParts` entries and checks `dst.Parts[p.name]` existence BEFORE any byte copy. If any of the 5 parts already exists in the target, the cloner returns `ErrCloneTargetNotEmpty` immediately — no `MarkModified`, no relationship added, no content-type Override set. The target is left in its pre-call state. This is the same guard shape as `opc.Open`'s mandatory `[Content_Types].xml` check (package.go:175-178). Test `TestCloneStyles_ErrCloneTargetNotEmpty` asserts the target's pre-existing styles.xml data is unchanged after the error (atomicity regression guard). |
| T-02-15 | Information Disclosure / Tampering | `CloneStyles` — relationship rId collision in target | medium | mitigate | `Relationships.NextRID` (relationships.go:138-145) is a high-water-mark allocator: it scans existing rIds on first call (`rescan`:63-71) and issues the next integer. Reuse is impossible by construction (OPC-06). The cloner calls `NextRID` once per cloned part, so 5 fresh rIds are allocated. `opc.Save` validates unique ids and dangling targets before writing (relationships.go:161-191) — a collision would surface at save time, not silently corrupt the package. |
| T-02-16 | Tampering | `CloneStyles` — content-type Override key missing leading slash | medium | mitigate | The PATTERNS critical flag (02-PATTERNS line 129) documents that `ContentTypes.Overrides` keys are OPC-absolute with a leading `/`. The cloner sets `dst.ContentTypes.Overrides["/"+p.name] = p.ct` — the leading slash is explicit in the code. `ContentTypes.TypeFor` (contenttypes.go:60-75) reads `c.Overrides["/"+partName]` — without the slash, `TypeFor` would miss the override and `opc.Save` would fail with "part has no content type" (package.go:280). Test `TestCloneStyles_ContentTypeOverrides` asserts the leading slash is present in every key (regression guard). |
| T-02-17 | DoS | `CloneStyles` — idempotent re-clone on already-cloned target | low | accept | Calling `CloneStyles` twice on the same dst fails on the second call with `ErrCloneTargetNotEmpty` (the first call populated the 5 parts — D-08 fresh-empty-target policy). This is by design (D-08), not a vulnerability — the error is clear and the target is not corrupted. Test `TestCloneStyles_IdempotentFails` asserts this behavior. |
| T-02-SC | Tampering | npm/pip/cargo installs | n/a | n/a | No package manager in this plan — stdlib + internal packages only (PROJECT.md zero-dep constraint). RESEARCH §Package Legitimacy Audit: "Not applicable". No `[ASSUMED]`/`[SUS]`/`[SLOP]` packages to gate. |
