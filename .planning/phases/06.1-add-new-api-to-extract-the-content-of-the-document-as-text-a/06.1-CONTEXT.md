# Phase 06.1: Text Extraction & Markdown Conversion — Context

**Gathered:** 2026-07-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Three connected capabilities on the `wordingo` Document type:
1. **Text extraction** — `doc.ExtractText(opts)` returns all document text as a flat string
2. **Markdown export** — `doc.ToMarkdown(opts)` converts docx content to GitHub-Flavored Markdown (GFM)
3. **Markdown import** — `wordingo.CreateFromMarkdown(md)` creates a new Document from GFM; `doc.ImportMarkdown(md)` appends GFM content to an existing document

All three operate on the existing Document model (paragraphs, runs, tables, headers, footers). No new OPC-level work. Stdlib only — no external Markdown parser dependency.

</domain>

<decisions>
## Implementation Decisions

### Text Extraction API
- **D-01:** `doc.ExtractText(opts ExtractOpts) (string, error)` — method on Document. Returns plain text with no formatting information.
- **D-02:** `ExtractOpts` mirrors `MergeOpts` pattern from Phase 6: struct with `Body`, `Tables`, `Headers`, `Footers` booleans. All default true. `nil` opts = scan all.
- **D-03:** `ExtractOpts.Separator` string field — delimiter between extracted elements. Default `"\n"`.
- **D-04:** Non-text run elements (images, line breaks, tabs, hyperlinks, drawings) silently skipped. Only `w:t` text content included.
- **D-05:** Table cells separated by `Separator`. Rows separated by `Separator`. No grid/position metadata.

### Markdown Export (docx → GFM)
- **D-06:** `doc.ToMarkdown(opts ExtractOpts) (string, error)` — method on Document. Reuses same `ExtractOpts` to control which parts are included.
- **D-07:** Block elements mapped: headings (`Heading1`–`6` → `#`–`######`), paragraphs → plain text, ordered lists → `1.`, bullet lists → `-`, tables → GFM pipe tables, code blocks → fenced `` ``` ``.
- **D-08:** Inline formatting: bold → `**`, italic → `*`, strikethrough → `~~`, code → `` ` ``. Underline, highlight, font/size/color stripped.
- **D-09:** Hyperlinks → `[text](url)`. Images → embedded base64 (existing PNG/JPEG from `drawing.go` DrawingML anchors only, no vector formats).
- **D-10:** Page breaks skipped. Headers/footers included per `ExtractOpts`.

### Markdown Import (GFM → docx)
- **D-11:** `wordingo.CreateFromMarkdown(markdown string) (*Document, error)` — standalone function. Creates blank document with default styles, imports content.
- **D-12:** `doc.ImportMarkdown(markdown string)` — method on Document. Appends parsed content to existing document body. After all body paragraphs (v1 limitation per Phase 5 D-24).
- **D-13:** Block elements parsed: headings, paragraphs, ordered/bullet lists, pipe tables, fenced code blocks. Blockquotes, horizontal rules, task lists, HTML — **not** supported.
- **D-14:** Inline formatting parsed: bold `**`, italic `*`, code `` ` ``, links `[text](url)`, images `![alt](url)`. Strikethrough, autolinks, HTML inline — **not** supported.
- **D-15:** Heading levels `#`–`######` map to `Heading1`–`Heading6` named styles. Uses template heading styles if from template, or default heading styles for fresh documents.
- **D-16:** Markdown parser implemented in-house using Go stdlib (`strings`, `bufio`, `regexp`). No external dependency.

### Code Organization
- **D-17:** Three files at root package level: `extract.go` (text extraction), `markdown.go` (to-markdown export), `markdown_import.go` (markdown import). Follows existing file-per-responsibility pattern.
- **D-18:** Internal Markdown parser lives in `internal/markdown/parser.go` — separate internal package, consistent with `internal/opc`, `internal/wml` layered architecture.

### the agent's Discretion
- Exact `ExtractOpts` struct field naming and zero-value defaults
- Separator behavior at end of last element (trailing separator or not)
- Pipe table column alignment parsing (alignment from `:---` vs `----`)
- Code block language hint handling (stored as paragraph style or skipped)
- List nesting depth limit (9 levels per OOXML, practical limit lower)
- Base64 image format detection (PNG vs JPEG from bytes)
- Table cell content parsing (inline formatting inside table cells)
- Error handling for malformed markdown (best-effort parse vs strict)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `merge.go` — `walkHeaderParts`/`walkFooterParts` functions walk header/footer parts with decode-edit-encode cycle. **Directly reusable** for text extraction and markdown export.
- `merge.go` — `replaceInTable` walks table cell paragraphs. Reusable for extracting text from tables.
- `merge.go` — `MergeOpts`/`ScopedParts` pattern. `ExtractOpts` follows the exact same shape.
- `paragraph.go` — `Paragraph.Text()` returns concatenated run text. Ready to use as building block.
- `header.go` — `Header.Paragraphs()`, `Footer.Paragraphs()` — access paragraphs in header/footer parts.
- `body.go` — `Document.Body()` returns ordered `[]BodyElement` interleaving paragraphs and tables.
- `image.go` / `internal/wml/drawing.go` — DrawingML types for image embedding. Needed for base64 image export.
- `hyperlink.go` — Hyperlink paragraph structure (CT_Hyperlink with child runs).

### Established Patterns
- Wrapper-over-schema with `X()` escape hatch
- Builder chaining returns receiver
- Errors not panics, `Warnings()` for non-fatal issues
- Single public package; internal packages for implementation
- Stdlib only, zero external dependencies

### Integration Points
- Text extraction walks the same Document parts as Merge — body paragraphs, table cells, header/footer paragraphs
- Markdown export adds a new method on Document — no structural changes needed
- Markdown import needs to create paragraphs, runs, tables, lists — all existing API surface
- Internal Markdown parser in `internal/markdown/` — new subpackage, follows the internal package pattern
- Imported content may reference named styles (Heading1-6) — resolver must be accessible

</code_context>

<specifics>
## Specific Ideas

- Text extraction reuses `walkHeaderParts`/`walkFooterParts` from merge.go almost verbatim
- Pipe table parsing is the trickiest GFM feature — columns with alignment, escaped pipes in content
- List import needs to generate numbering definitions (reuse Phase 5 `list.go` patterns)
- Base64 images inline in markdown: `![alt](data:image/png;base64,...)` — read raw bytes from part, encode, embed
- Code blocks import as monospace paragraphs (no equivalent docx element for code blocks — simplest approach is Normal paragraph with Consolas/Courier font)
- CreateFromMarkdown returns a document with default styles from Create() then imports content

</specifics>
