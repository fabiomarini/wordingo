## Summary

Phase 06.1 adds three capabilities to the `wordingo` Document type: (1) plain text extraction via `doc.ExtractText(opts)`, (2) GitHub-Flavored Markdown export via `doc.ToMarkdown(opts)`, and (3) Markdown import via `wordingo.CreateFromMarkdown(md)` and `doc.ImportMarkdown(md)`. All three reuse existing infrastructure: `walkHeaderParts`/`walkFooterParts` from merge.go, `Paragraph.Text()` for run concatenation, `Body()` for interleaved paragraph/table iteration, and the existing Document builder API for creating paragraphs, runs, tables, and lists during import.

**Primary recommendation:** Implement as three root-package files (`extract.go`, `markdown.go`, `markdown_import.go`) plus one internal package (`internal/markdown/parser.go`) for the GFM parser. Follow the established `MergeOpts` pattern for `ExtractOpts` and the established internal package pattern for the parser.

### Locked Decisions

#### Text Extraction API
- **D-01:** `doc.ExtractText(opts ExtractOpts) (string, error)` — method on Document. Returns plain text with no formatting information.
- **D-02:** `ExtractOpts` mirrors `MergeOpts` pattern from Phase 6: struct with `Body`, `Tables`, `Headers`, `Footers` booleans. All default true. `nil` opts = scan all.
- **D-03:** `ExtractOpts.Separator` string field — delimiter between extracted elements. Default `"\n"`.
- **D-04:** Non-text run elements (images, line breaks, tabs, hyperlinks, drawings) silently skipped. Only `w:t` text content included.
- **D-05:** Table cells separated by `Separator`. Rows separated by `Separator`. No grid/position metadata.

#### Markdown Export (docx → GFM)
- **D-06:** `doc.ToMarkdown(opts ExtractOpts) (string, error)` — method on Document. Reuses same `ExtractOpts` to control which parts are included.
- **D-07:** Block elements mapped: headings (`Heading1`–`6` → `#`–`######`), paragraphs → plain text, ordered lists → `1.`, bullet lists → `-`, tables → GFM pipe tables, code blocks → fenced `` ``` ``.
- **D-08:** Inline formatting: bold → `**`, italic → `*`, strikethrough → `~~`, code → `` ` ``. Underline, highlight, font/size/color stripped.
- **D-09:** Hyperlinks → `[text](url)`. Images → embedded base64 (existing PNG/JPEG from `drawing.go` DrawingML anchors only, no vector formats).
- **D-10:** Page breaks skipped. Headers/footers included per `ExtractOpts`.

#### Markdown Import (GFM → docx)
- **D-11:** `wordingo.CreateFromMarkdown(markdown string) (*Document, error)` — standalone function. Creates blank document with default styles, imports content.
- **D-12:** `doc.ImportMarkdown(markdown string)` — method on Document. Appends parsed content to existing document body. After all body paragraphs (v1 limitation per Phase 5 D-24).
- **D-13:** Block elements parsed: headings, paragraphs, ordered/bullet lists, pipe tables, fenced code blocks. Blockquotes, horizontal rules, task lists, HTML — **not** supported.

- **D-15:** Heading levels `#`–`######` map to `Heading1`–`Heading6` named styles. Uses template heading styles if from template, or default heading styles for fresh documents.
- **D-16:** Markdown parser implemented in-house using Go stdlib (`strings`, `bufio`, `regexp`). No external dependency.

### Pattern 1: Scoped Parts Iteration (Text Extraction)
**What:** ExtractText reuses the exact `walkHeaderParts`/`walkFooterParts` pattern from merge.go, scanning only the parts indicated by `ExtractOpts.ScopedParts`. Each paragraph's text is obtained via `Paragraph.Text()` — which already concatenates all `w:t` values across runs — then elements are joined with the configured Separator.

**When to use:** Always. The walk functions handle the full decode-edit-encode cycle for header/footer parts, and markdown export uses the same walking pattern.

**Example:**
```go
// extract.go (pattern — reuses merge.go walk infrastructure)
func (d *Document) ExtractText(opts *ExtractOpts) (string, error) {
    if opts == nil {
        opts = &ExtractOpts{ScopedParts: ScopedParts{Body: true, Tables: true, Headers: true, Footers: true}}
    }
    var b strings.Builder
    sep := opts.Separator
    if sep == "" {
        sep = "\n"
    }

    if opts.ScopedParts.Body {
        for _, p := range d.doc.Body.P {
            text := paragraphText(p)
            if text != "" {
                b.WriteString(text)
                b.WriteString(sep)
            }
        }
    }

    if opts.ScopedParts.Tables {
        for _, tbl := range d.doc.Body.Tbl {
            for ri, row := range tbl.Tr {
                for ci, cell := range row.Tc {
                    for _, p := range cell.P {
                        text := paragraphText(p)
                        if text != "" {
                            b.WriteString(text)
                        }
                    }
                    if ci < len(row.Tc)-1 {
                        b.WriteString(sep) // cell separator
                    }
                }
                if ri < len(tbl.Tr)-1 {
                    b.WriteString(sep) // row separator
                }
            }
        }
    }

    // Same for Headers/Footers via walkHeaderParts/walkFooterParts...
    d.dirty = false // extraction is read-only
    return strings.TrimSuffix(b.String(), sep), nil
}
```

### Pattern 2: Block-Aware Export Walk (Markdown Export)
**What:** ToMarkdown walks the same Document parts but emits GFM syntax instead of raw text. For each paragraph, it inspects `pStyle` (Heading1–6 → `#` prefix), `numPr` (list detection), and run `rPr` (inline formatting). Tables use a GFM pipe table emitter.

**When to use:** Always for export. The key detection logic is:
1. **Heading detection:** `Paragraph.Style()` returns style ID; check prefix `"Heading"` + suffix digit `1–6`
2. **List detection:** Check `PPr.NumPr != nil` on the CT_P; cross-reference numbering.xml to determine ordered vs bulleted
3. **Inline formatting:** For each run, inspect `RPr.B`, `RPr.I`, `RPr.Strike`, `RPr.U` to emit GFM delimiters
4. **Hyperlinks:** Paragraph has `CT_Hyperlink` children with `CT_R` children and rId to external URI in document.xml.rels
5. **Images:** Run has `Drawing` field; extract source image data from part bytes via relationship

**Example (inline export pattern):**
```go
// markdown.go — inside paragraph export
func exportRunText(r *wml.CT_R) string {
    if r.T == nil {
        return ""
    }
    text := r.T.Value
    if r.RPr == nil {
        return escapeMarkdown(text)
    }
    if r.RPr.B != nil && (r.RPr.B.Val == nil || *r.RPr.B.Val) {
        text = "**" + text + "**"
    }
    if r.RPr.I != nil && (r.RPr.I.Val == nil || *r.RPr.I.Val) {
        text = "*" + text + "*"
    }
    if r.RPr.Strike != nil && (r.RPr.Strike.Val == nil || *r.RPr.Strike.Val) {
        text = "~~" + text + "~~"
    }
    return text
}
```

### Pattern 3: Line-Based GFM Parser (Markdown Import)
**What:** The internal parser processes markdown in two phases matching CommonMark/GFM strategy: (1) block parsing via `bufio.Scanner` lines, identifying heading markers, fence delimiters, list markers, and table separators; (2) inline parsing per block, scanning for `**`, `*`, `` ` ``, `[text](url)`, `![alt](url)`.

**When to use:** Always. No backtracking needed for the supported subset (no blockquotes, no setext headings, no thematic breaks).

### Anti-Patterns to Avoid
- **Mixing extraction and modification:** ExtractText and ToMarkdown are read-only operations. Do NOT set `d.dirty = true` during extraction/export. The walkHeaderParts/walkFooterParts functions from merge.go modify parts — for extraction, use a read-only variant.
- **Full CommonMark compliance:** D-13 explicitly limits the supported block/inline subset. Do not attempt full GFM spec compliance (no blockquotes, no setext headings, no autolinks, no HTML).
- **Over-nesting list detection:** Lists can nest 9 levels in OOXML. The parser should track nesting depth by indentation, but cap practical depth at a reasonable limit per agent discretion.
- **Re-encoding parts for read-only access:** The `walkHeaderParts`/`walkFooterParts` in merge.go re-encodes and calls `MarkModified`. Create separate `readHeaderParts`/`readFooterParts` that only decode, read text, and do not re-encode.

The novel work is string-to-WML mapping (the GFM parser) and WML-to-string mapping (the GFM exporter), both of which are pure string transformations with no new OPC or WML schema work.

## Common Pitfalls

### Pitfall 1: Run-Level Formatting Gaps in Paragraph.Text()
**What goes wrong:** `Paragraph.Text()` concatenates only `r.T` text values. Hyperlink text lives in `CT_Hyperlink.R[].T`, not in `CT_P.R[]`. If ToMarkdown/ExtractText walks only `CT_P.R`, hyperlink text is silently dropped.
**Why it happens:** The paragraph's WML struct has both `CT_P.R` (direct runs) and `CT_P.Hyperlink` (hyperlinks with child runs). `Paragraph.Text()` iterates only `R`.
**How to avoid:** For both extraction and export, build a helper that iterates `P.R` for direct runs AND `P.Hyperlink` for hyperlink child runs. For export, hyperlinks additionally need the target URI resolved via the relationship.
**Warning signs:** Missing text in exported markdown for paragraphs containing hyperlinks.

### Pitfall 2: Nested Numbering Definition Lookup for Lists
**What goes wrong:** A paragraph with `numPr` references a `numId` and `ilvl`. Determining whether it's ordered or bulleted requires reading `numbering.xml`, resolving `num → abstractNum → lvl[ilvl].numFmt`. This is a multi-step indirect lookup that is easy to skip.
**Why it happens:** The paragraph itself only stores `numId` + `ilvl`, not the list type. The numbering definition lives in a separate package part.
**How to avoid:** Reuse the numbering reading infrastructure from list.go (`readOrCreateNumbering`) for the lookup. Cache the abstractNum mapping for performance.
**Warning signs:** Ordered lists exported as bulleted (or vice versa).

### Pitfall 3: GFM Pipe Table Escaping
**What goes wrong:** If cell content contains pipe `|` or backslash `\`, the generated pipe table is malformed GFM.
**Why it happens:** GFM pipe tables use `|` as column delimiter. Literal pipes in content must be escaped as `\|`. Backslashes must also be escaped.
**How to avoid:** Escape `|` and `\` in cell content before placing in pipe table. Per GFM spec §4.10, content may contain inline formatting; pipes inside code spans are protected.
**Warning signs:** Imported markdown table has wrong column count after re-import.

### Pitfall 4: Inline Formatting Spanning Multiple Runs
**What goes wrong:** Word can split a formatted phrase across multiple runs (e.g., `<w:r><w:rPr><w:b/></w:rPr><w:t>Hello</w:t></w:r><w:r><w:rPr><w:b/></w:rPr><w:t> World</w:t></w:r>`). Exporting each run independently produces `**Hello** **World**` instead of `**Hello World**`.
**Why it happens:** Runs are formatting scopes; consecutive runs with identical formatting should be merged for clean GFM output.
**How to avoid:** Group consecutive runs with identical formatting (same bold/italic/strikethrough state) and emit a single formatting span. This is the same problem as split-run placeholder detection in merge.go but inverted — instead of splitting, we merge.
**Warning signs:** Exported markdown has `****` empty formatting or adjacent identical formatting delimiters.

### Pitfall 5: Base64 Image Size in Markdown
**What goes wrong:** Inline base64 images can make the exported markdown file extremely large. A single 500KB JPEG becomes ~680KB of base64 text in the markdown.
**Why it happens:** GFM doesn't support external image references in a local .md file; embedding is the only portable option.
**How to avoid:** This is expected behavior per D-09. Document the size implication and note that downstream tools (pandoc, etc.) may struggle with very large markdown files containing embedded images. Keep the implementation but consider it a known limitation.
**Warning signs:** Export time is dominated by base64 encoding of image data.

### Pitfall 6: Pipe Table Import with Trailing Pipe
**What goes wrong:** GFM allows optional trailing pipes: `| a | b |` and `| a | b` are both valid. The parser must handle both variants correctly.
**Why it happens:** The GFM spec (§4.10) says "Each cell can contain one or more pipes" — leading and trailing pipes are stripped during parsing.
**How to avoid:** After splitting on pipe, trim leading empty cell (before first `|`) and trailing empty cell (after last `|`). Per spec: "The outer pipes are removed; the row is split at internal pipes."
**Warning signs:** Imported table has empty first or last column.

```go
// Source: Derived from CONTEXT.md D-01..D-05 and existing MergeOpts pattern

type ExtractOpts struct {
    ScopedParts ScopedParts
    Separator   string
}

func (d *Document) ExtractText(opts *ExtractOpts) (string, error) {
    // nil opts = default all parts
    if opts == nil {
        opts = &ExtractOpts{
            ScopedParts: ScopedParts{Body: true, Tables: true, Headers: true, Footers: true},
            Separator: "\n",
        }
    }
    sep := opts.Separator
    if sep == "" {
        sep = "\n"
    }

    var b strings.Builder

    if opts.ScopedParts.Body {
        for _, p := range d.doc.Body.P {
            text := paragraphText(p)
            if text != "" {
                b.WriteString(text)
                b.WriteString(sep)
            }
        }
    }

    if opts.ScopedParts.Tables {
        for _, tbl := range d.doc.Body.Tbl {
            for ri, row := range tbl.Tr {
                for ci, cell := range row.Tc {
                    for _, p := range cell.P {
                        text := paragraphText(p)
                        if text != "" {
                            b.WriteString(text)
                        }
                    }
                    if ci < len(row.Tc)-1 {
                        b.WriteString(sep)
                    }
                }
                b.WriteString(sep) // row separator
            }
        }
    }

    if opts.ScopedParts.Headers {
        d.readHeaderParts(func(hdr *wml.CT_Hdr) {
            for _, p := range hdr.P {
                text := paragraphText(p)
                if text != "" {
                    b.WriteString(text)
                    b.WriteString(sep)
                }
            }
        })
    }

    if opts.ScopedParts.Footers {
        d.readFooterParts(func(ftr *wml.CT_Ftr) {
            for _, p := range ftr.P {
                text := paragraphText(p)
                if text != "" {
                    b.WriteString(text)
                    b.WriteString(sep)
                }
            }
        })
    }

    result := b.String()
    // Trim trailing separator
    if len(result) >= len(sep) {
        result = strings.TrimSuffix(result, sep)
    }
    return result, nil
}

// paragraphText extracts text from CT_P, including hyperlink child runs.
// Does NOT include non-text elements (br, tab, cr, drawing).
func paragraphText(p *wml.CT_P) string {
    var b strings.Builder
    for _, r := range p.R {
        if r.T != nil {
            b.WriteString(r.T.Value)
        }
    }
    for _, hl := range p.Hyperlink {
        for _, r := range hl.R {
            if r.T != nil {
                b.WriteString(r.T.Value)
            }
        }
    }
    return b.String()
}
```

```go
func (d *Document) readHeaderParts(fn func(hdr *wml.CT_Hdr)) {
    if d.doc.Body.SectPr == nil {
        return
    }
    rels := d.pkg.Rels["word/document.xml"]
    if rels == nil {
        return
    }
    for _, ref := range d.doc.Body.SectPr.HdrFtrRef {
        rel := findRelByID(rels, ref.ID)
        if rel == nil {
            continue
        }
        target := path.Join("word", rel.Target)
        part, ok := d.pkg.Parts[target]
        if !ok {
            continue
        }
        partBytes, err := readPartBytes(part)
        if err != nil {
            continue
        }
        var hdr wml.CT_Hdr
        dec := xmlutil.NewSafeDecoder(bytes.NewReader(partBytes), opc.MaxPartBytes)
        if err := dec.Decode(&hdr); err != nil {
            continue
        }
        fn(&hdr)
        // NOTE: No re-encode or MarkModified — read-only.
    }
}
```

### GFM Pipe Table Generation
```go
// Source: GFM Spec §4.10 (Tables extension)

func generatePipeTable(headers []string, rows [][]string) string {
    var b strings.Builder

    // Header row
    b.WriteString("| ")
    for i, h := range headers {
        if i > 0 {
            b.WriteString(" | ")
        }
        b.WriteString(escapePipeCell(h))
    }
    b.WriteString(" |\n")

    // Separator row (left-aligned default)
    b.WriteString("| ")
    for i := range headers {
        if i > 0 {
            b.WriteString(" | ")
        }
        b.WriteString("---")
    }
    b.WriteString(" |\n")

    // Data rows
    for _, row := range rows {
        b.WriteString("| ")
        for ci := 0; ci < len(headers); ci++ {
            if ci > 0 {
                b.WriteString(" | ")
            }
            if ci < len(row) {
                b.WriteString(escapePipeCell(row[ci]))
            }
        }
        b.WriteString(" |\n")
    }

    return b.String()
}

func escapePipeCell(s string) string {
    s = strings.ReplaceAll(s, "\\", "\\\\")
    s = strings.ReplaceAll(s, "|", "\\|")
    return s
}
```

## Open Questions

1. **List detection for export: how to resolve ordered vs bulleted from numPr?**
   - What we know: `Paragraph.X().PPr.NumPr` contains `numId` and `ilvl`. `numbering.xml` maps `numId → abstractNumId`, then `abstractNum` contains `lvl[numFmt]` for each level.
   - What's unclear: Exact path to read and cache this mapping efficiently without reimplementing the style engine's numbering resolver.
   - Recommendation: Reuse `readOrCreateNumbering()` from list.go for reading, then build a simple `map[int64]map[int64]string` cache (numId→ilvl→numFmt). The style engine's internal numbering resolver is more complex than needed here.

2. **Code block representation in docx on import?**
   - What we know: D-7 says export maps fenced code blocks to ` ``` ` blocks. On import, there's no native docx code block element.
   - What's unclear: Import creates monospace paragraphs (Consolas/Courier font via SetFont). But should code blocks get a custom style, or just Normal + monospace + fenced in markdown export?
   - Recommendation: Import as Normal paragraphs with Consolas font (D-7's simplest approach). On re-export, consecutive monospace paragraphs could be grouped into a fenced block, but that's beyond v1 scope.

3. **Inline formatting inside table cells on import?**
   - What we know: D-14 says inline formatting (bold, italic, code, links, images) is parsed. D-16 says agent discretion for table cell content parsing.
   - What's unclear: Whether inline formatting should be parsed inside pipe table cells during import, or table cell content should be plain text only.
   - Recommendation: Parse inline formatting inside table cells for consistency (cells may contain **bold** or `` `code` ``). Skip links/images in cells for v1 simplicity (rare in tables).
